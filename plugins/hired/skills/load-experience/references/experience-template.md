# Experience page template

The shape of the **Experience** page, written as a child of Pipeline Config in Notion.
score-roles reads this page at the start of every run and cites it in the summaries.

Everything below is a shape to fill from the user's own documents. The rule from the skill
file holds here: every line must be traceable to something the user wrote or confirmed. A
blank section is fine. An invented one poisons every score that cites it.

Keep it readable. This is a page the user will open when a score surprises them, and the
first thing they will do is check whether the evidence behind it is actually theirs.

---

## Summary

Two or three lines. Current or most recent title, total years of relevant experience, the
scope they have carried, and the domains they are credible in. This is what the scorer
reads first.

## Roles

Newest first. One block each, no more than the last five or six roles - beyond that,
compress into a line.

- **[Title]**, [Company] · [start]–[end] · [IC / manager, team size]
  - Scope: [org size, budget, revenue, users, scale - whatever the resume states]
  - [Accomplishment, quantified]
  - [Accomplishment, quantified]

## Proof points

The five or six strongest, most specific accomplishments, confirmed by the user in Step 4.
These are what a job description gets compared against. Each one names what changed and by
how much.

- [Accomplishment with a number and the mechanism behind it]

If the setup interview also produced proof points, merge them here rather than keeping two
lists. One list, or the scorer picks a favourite.

## Domains

- **Deep**: [industries, product surfaces, business models with real shipping history]
- **Adjacent**: [one project or a partial year - real, but do not oversell it]
- **Claimed but thin**: [anything the resume asserts without evidence behind it]

The three tiers matter. A scorer that cannot tell deep from thin will award a role full
marks on a domain the user touched once.

## Skills and tools

Only what the documents state. Group loosely; do not build a keyword list. The scorer
matches on substance, not vocabulary, so this section is a reference rather than a
checklist.

## How they position themselves

From the cover letters. What they lead with when they want the job, which accomplishments
they reach for, and the words they use for their own work. Note which role each cover
letter was written for.

Omit this section entirely if there were no cover letters. Do not reconstruct it from the
resume.

## Standout evidence

Optional, and only if the rubric has standout logic. For each standout dimension the
rubric names, the concrete evidence from these documents that the user can actually claim.
This is what turns a standout rule from an assertion into something the scorer can check.

- [Rubric standout dimension]: [the evidence, from the resume or a cover letter]

## Constraints of record

Only what the documents state: location, work authorization, notice period, languages,
required credentials. If the setup interview already captured these on the Profile, note
any conflict here rather than overwriting - the user resolves it, not you.

## Gaps and caveats

What the scorer should know about the limits of this profile.

- [Employment gap, or a resume that stops before today]
- [Scope stated vaguely]
- [Anything the user asked to drop, and that it was dropped]

## Provenance

- Sources: [filenames or "pasted text", and how many cover letters]
- Loaded: [date]
- Confirmed with the user: [yes / partially, with what is outstanding]

Keep this section. When a score cites evidence the user does not recognise six weeks from
now, this is the line that tells them which document it came from.
